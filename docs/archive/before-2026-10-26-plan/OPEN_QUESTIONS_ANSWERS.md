## 1. 持续只读、租约与接管

### 已能回答

- 健康首连接在隔离服务上可以取得租约，所以目前不能断言“无头浏览器必然故障”或“已关闭连接仍持续心跳”。本次生产端曾观察到一条已建立 TCP 连接，但这不能证明它就是租约持有者，亦不能判断是浏览器、测试进程还是其他连接。
- 页面真正关闭后不能继续由该页面发应用心跳；但隐藏页面、残留浏览器上下文、HMR 重复初始化或重连定时器残留可能仍持有有效连接。先记录证据，不要靠不断重启/禁用租约掩盖。
- 服务端给每个连接分配 connectionId，日志记录 owner/browserInstanceId、授予/续租/到期/释放时间、epoch、最后应用心跳、close 原因和当前持有者（不记录聊天或密钥）。客户端公开诊断只提供自己是否执行端、到期时间、重连状态等必要信息。

### 定案

- 应用心跳维持执行租约，建议 5 秒续租、20 秒有效期；8 秒配 5 秒心跳余量偏小。用服务端单调时钟计算有效期，不相信客户端时间。
- 服务端 ping/pong 可辅助发现传输失联，**不能仅靠 pong 自动延长执行租约**：连接活着不等于应用能安全执行。
- 所有变更入口统一校验连接是持有者、租约尚有效、epoch 正确、会话匹配。state_snapshot、chat 状态、plan_result、对账确认不能成为旁路；必需协议字段缺失应拒绝，不能仅“如果带了才校验”。
- 到期应主动撤销/广播并增加 fencing 代际，不能仅等另一个 hello 才发现。客户端失去租约立即停止控制，漫游与计划均停。旧心跳不能让已经到期的 epoch 复活。
- 单个 BrainClient 最多一个活动 socket、一套心跳/重连/接管计时器。重连回调绑定 socket generation；提供 dispose，关闭页面/销毁实例时清理。旧 socket 的 close 不能关闭或重连新的 socket。
- 只读页可看场景、打开本地只读面板；不能因此让角色转身、停漫游、改变聊天状态或发消息。禁止读取不属于自己的历史/记忆。取得租约并完成对账后才可进入主动聊天。
- 接管后必须拉权威快照、任务和账本，完成握手后再放行。当前 onSnapshot 只应用一次、onReconcile 先发本地快照的顺序不合格：新页面初始坐标不能反向覆盖持久位置。

## 3. 重连对账

不是“比较 originWs 后 endTask”。socket 身份只证明连接变化，不证明动作完成。

- 断线/服务重启时保留 taskId、generation、原目标、计划、每步结果、派发/接受/完成记录、最新快照和对象状态。缺证据标 unknown，禁漫游和副作用。
- 已知动作完成、仅检查未结束：刷新快照后继续 review，不重发旧计划。
- 确认尚未派发/执行的规划：对账后可重新规划。
- 部分执行：保留实际结果，检查或规划剩余部分。
- 是否已执行不明：保持 unknown；允许用户明确放弃该旧任务后提出新目标，但不默认重投/重走。放弃不抹掉历史事实。
- 对账中允许保留草稿；发送暂不接受，或者进入明确可见但不执行的待处理队列。第一版采用“同步中，发送禁用”较简单，不制造用户以为已经发送的假记录。
- 启动后显示“连接已恢复，正在核对上次动作”；无法核对显示具体未知事项和可选的结束旧任务入口。不要单凭重连成功清红图标、恢复漫游。
- task/plan/message ID 用 UUID 或持久单调序列，至少含稳定会话命名空间。当前 nextTask=100、generation=0 每次重启重置，而旧 ledger 保留，会产生 ID 冲突。

## 4. 上下文预算

`chars*0.6 + 只裁历史1200tokens` 可作为临时指标，不能作为整轮预算验收。没有适配当前模型的 tokenizer 不阻塞第一版；不要拿其他模型 tokenizer 冒充精确 DeepSeek token 数。

- 延续原契约：输入目标 8000、输出预留 2000，并受实际模型上下文上限限制。当前 max_tokens=800 也需与契约配置统一。
- 统计 system、能力/Schema、模板、快照、目标、账本、记忆、历史全部开销。字符估算不是可证明的保守上界，必须留余量、标明估算，并用 API 返回 usage 对比校准；不要对用户宣称精确。
- 原目标和活动任务证据放入独立固定字段，不依赖它们碰巧仍在最近历史里；即使很旧也保留。review 必须含原目标、所有相关已完成步骤和失败/unknown，防止重走。
- 裁剪完整对话轮，保留最近至多 12 轮，区别于目前 slice(-12) 的 12 条消息。先删无关历史，再缩减非关键摘要，不能删掉关键账本或截断 JSON。
- 固定关键内容本身超预算则报 CONTEXT_TOO_LARGE。不能删掉最新用户消息或系统规则继续执行。

## 5. 记忆

已有 CONTEXT_MEMORY.md 足以定案，无需再让用户重复确认原则。

- candidate 不作为已确认偏好注入。可以先存 candidate 开发，但没有查看/确认/删除 UI 不能宣告 E 完成。
- 普通“我喜欢……”由用户在记忆列表确认；明确“记住/以后叫我/以后回答……”允许按原契约通过服务端可靠来源检查后确认。模型提案本身不能直接写 confirmed；来源歧义就留 candidate。
- 当前 validateProposals 只看传入 sourceMessageId 非空，任何模型内容都能挂到当前消息上，不算来源验证。必须核对真实消息属于该 owner、ID存在、sourceQuote匹配以及确实是用户表达而非引用/假设。历史消息也需要真实持久 ID。
- 白名单按原契约统一为 preferred_name、response_language、response_style、ordinary_interest；不能提示词用一套而服务器用 nickname/style/interest。若需旧数据迁移，显式映射并记录版本。
- 记忆请求操作包括 upsert/delete，需支持来源、owner、修订和 tombstone；删除后后续检索、候选提取及摘要不能复活。现在没有摘要，不必为清理而先实现摘要，但预留 derived/sourceMemoryIds 与删除过滤。
- ownerScope 是服务端签发/验证的用户或会话作用域，不是 IP、WebSocket ID、当前 lease 持有者。可在同一浏览器可信会话内保持；不同浏览器默认独立，不因共用角色自动共享偏好。尚无跨浏览器身份系统时不要擅自推断同一用户。
- 推理时读当前 store.state，而不是启动时 storeSeed 的缓存。现代码使用 confirmedMemories(storeSeed.memories)，后续确认/删除不能保证及时反映。

## 6. 聊天关闭守卫

- chatOpen 属于当前主动交互会话，并绑定执行连接/epoch；不是所有浏览器可写的全局布尔。只读面板是否打开是本地 UI 状态。
- 刷新/执行端断开后旧聊天打开状态失效，默认 closed；草稿/历史与聊天开关分离保存。新页面取得租约和完成状态同步后仍需按既定点击角色流程进入聊天。
- 手动关闭、两分钟超时、断线、执行权撤销统一经一个关闭入口更新本地状态并通知服务端；服务端断线也自行清理，不能完全依赖 pagehide 消息一定送达。
- 已证实超时回调只隐藏气泡，确实缺 chat_closed。要修。
- 活动事件先判旧 deadline 是否超时，再决定是否续期；鼠标提交不续期。IME Enter 已补，是进展，但不代表全部超时边界完成。
- 聊天关闭不取消仍在执行的任务；任务完成之前不漫游。角色点击/显式新指令的抢占按 Coordinator 规则处理。

## 7. JSON 还是 SQLite

**不要求为了库名立即迁移 SQLite，JSON 可暂时用于单进程小规模实现；但现在的存储语义不足。** 使用抽象 store，先保证可恢复证据与一致性，后续再迁移。

- 保存 schemaVersion、作用域、消息时间/ID、完整任务/计划、结果、快照修订、记忆修订/删除记录。
- 原子 rename 防止半文件，不等于可靠事务。当前写错误只 console.error、计划先发后等防抖落盘，无法证明持久派发。关键 dispatch/result/ownership 记录必须可靠写入后再确认，失败则阻止产生未登记副作用；高频位置可防抖。
- 不要在“完成”时以 {state:'done', reply} 覆盖已存 result；合并状态并保留证据。不要把 character 与 task 分散到两文件后不记录共同 revision。
- 当前损坏文件直接当空状态是危险回退：会丢失执行证据。保留损坏文件并报恢复错误，不能伪装全新会话开始行动。
- 30 天清理按 createdAt 处理已结束且不被活动任务引用的历史；当前任务、unknown、未完成账本、来源仍需的记录保留。不要无限保留所有聊天，也不要一刀切清空账本。
- 服务重启后的 unknown 任务必须保留，不能清理。进程重启测试应检验能恢复目标和执行结果，不只检验 phase 字符串。

## 10. 除问题文档之外还需修的关键点

1. `main.ts` 没给 loco 实现 isMoving，Executor 使用可选调用并默认 false，所以 stopped 仍无法证明已停。内层 waitFor 15 秒返回正常，外层增加时长并没有解除最长移动的内层限制。超时应取消实际运动并等停稳，失败停机。
2. runOwned 忽略 waitBodySettled 返回 false；只等下半身，不等转向/尾巴等待清理；全局 cancelled 在新 run 重置。点击计划时 motionEpoch 增加，旧 finally 不再清 owner，仍可能残留 plan 所有者。需要真正单队列/运行代际和取消信号，而非只丢旧返回值。
3. canRoam 仍不检查 connected/readOnly/unknown/blocked；onConnection(false) 没置 errorActive。只读端会独立漫游并上报位置，与本轮已证实的服务端快照旁路叠加。
4. fail() 不校验旧 task/generation/request，仍 endTask 回 idle；旧异步异常可结束新任务。错误需要保留，增加按阶段重试入口，review 重试不得重播。
5. plan_result 缺身份校验，fencing 字段均可省略。客户端收计划也未验证 leaseEpoch/generation/planId 去重；不能只靠服务端结果端去重防止重复动作。
6. 同一计划完成保存会覆盖执行 result；任务主体未持久化，重启 ID 重用；needsReconcile 依赖运行内存 task。这不是完整对账系统。
7. 第 4 轮动作完成后在 review 前截断；180 秒只收结果时检查，不是主动预算。应允许第 4 次最终检查并主动执行超时停止。
8. server/llm.mjs 仍是旧简版 system 与手写 OUTPUT_CONTRACT；未同步最新固定/规划/检查模板、记忆契约和钢盆自主决策规则。禁用动作不应偷偷启用，但应提供 disabled 能力及原因。当前事件去重只在单测使用，不等于角色已会发现盆。
9. review 的角色状态仍可能是旧持久位置，原目标和前轮执行证据只靠短历史；完整快照与任务目标固定字段是必需项。
