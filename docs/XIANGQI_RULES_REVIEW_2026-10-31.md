# 象棋规则专项审查（2026-10-31）

## 结论与范围

**尚不符合完整 CCA2020 规则。基本行棋可以使用，但棋例裁决会误判胜负，不能仅将其描述为遗漏了少量高级规则。**

审查基线为 `0289367`。审查时 Mac、`origin/master`、服务器 `/home/xy3w/whale-app` 均为此版本，服务器与 Mac 的两份规则源码 SHA-256 一致。本次不修改业务代码、不重启服务。

对照中国象棋协会审定《象棋竞赛规则（2020版）》的行棋、胜负和、自然限着和棋例条款。规则书原文来源：

- [规则书 PDF 镜像](https://wdd66d.top/downloads/qigui/Xqqg2020.pdf)，113 页；核对第 8–9、15–18 页。该链接是原文件镜像，不是协会官网托管。
- [国家体育总局棋牌运动管理中心规程](https://www.sport.gov.cn/qpzx/n5387/c23462994/content.html)明确采用中国象棋协会审定的 2020 版，作为版本依据；详细条文以规则书为准。

按已确认产品设计，不把首版无棋钟、数字界面允许重新选择棋子、没有线下赛纪律处罚列为本次缺陷。它们与棋盘上的行棋及胜负裁决应区分。

## 发现的问题（按修复优先级）

### R1 / P1：没有产生新攻击的闲着，也会误判长捉负

位置：`server/xiangqi.mjs:301`、`:430–441`。

每手 `record.attacks` 收集的是全盘当前可吃子列表，不是这手棋产生的捉。裁决只求各手被攻击棋子的交集。

**已复现**：红车固定在 `(8,0)`，黑马固定在 `(4,0)`；双方另外各有一马来回跳，两将分别在 `(9,3)`、`(0,5)`。车从头到尾没动，也没有新产生的威胁。8 手后返回 `perpetual_chase / loser:red`。

规则 24.3、24.8 要区分着法实际产生的将、杀、捉和闲，不能把既存攻击自动归因于任何一手棋。

### R2 / P1：遗漏帅将、兵卒长捉例外，允许着法被判负

位置：`server/xiangqi.mjs:430–441`。

**已复现**：红帅在 `(8,3)`、`(8,4)` 间移动，黑炮在 `(7,3)`、`(7,4)` 间躲避，黑先走，形成循环。每步均通过合法性校验，程序却判红方长捉负。

26.1 允许帅将、兵卒本身长捉；26.1.1、26.1.2 另行区分与其他子配合产生的新攻击。当前模型没有记录攻击者及配合关系，无法正确应用这些条款。

### R3 / P1：长捉判定取最后盘面，循环起点会改变裁决性质

位置：`server/xiangqi.mjs:437–440`、`:379–394`。

历史记录中虽有攻击列表，但最终 `captureGain()` 只分析此刻的棋盘。对手刚躲开时就查不到可吃目标，之前连续追捉也会被抹掉。

**已复现两组合法循环**：红车横移追黑炮，黑炮横移躲避。循环从攻击前开始记录，最终为 `repetition`（和）；从同一循环的攻击后开始记录，最终为 `perpetual_chase`（红负）。完整走子记录在证据文件中。

应逐手在当时局面认定攻击性质，不能用最后一个局面替代历史。判定为需要变着与最终判负的时机还应按 R5 分开。

### R4 / P1：复杂棋例仍缺失，当前子力分数不能替代正式裁决

位置：`server/xiangqi.mjs:366–444`。

以下为**静态确认的覆盖缺口，未在本次逐个构造完整对局**：

- 无“杀”的识别，无法完整处理长杀、一将一杀、一将一捉、一杀一捉。
- 长捉只认所有攻击集合中的同一目标，不能完整处理交替追捉数子的循环（24.11、24.13）。
- 未按 26.9 比较双方禁止着法的责任；循环中先遍历到的追捉方会先被判负。
- 没有联合捉、完整互吃兑换、少根、假根、牵制及立即被杀等完整判定。
- 把马设为 4、炮设为 4.5，再比较一次交换分数，与规则的类别及例外裁决不等价。比如规则将马炮视为等值，并对强弱子、兵卒另有兑换规定；不能用棋力评估分数直接判输赢。
- 23.4 的多点交替攻击达九回合、即使未三次重复也可裁决的机制未实现。

### R5 / P1：缺少待判与变着阶段，重复即终局；开局早期也直接判和

位置：`server/xiangqi-service.mjs:181–194`、`server/xiangqi.mjs:404–444`。

除单方长将可立即判负外，23.5 对其他待判局面保留变着阶段；当前只要重复裁决返回对象，服务立即把棋局设为 `won/drawn`，没有待判、责任方、剩余变着回合和是否已变着的状态。

**已复现**：初始盘面，双方各一马往返两轮，8 手后直接返回和棋。4.3 规定 25 回合内出现此类不变作和的待判局面，应由红方变着，不变判负；当前没有这一分支。

这里不把“三次相同签名”直接等同于完整三循环验收；外来首着、首着吃子扣除等 23.2 细节还需专门用例。

### R6 / P2：自然限着只有无吃子 120 手，没有将军着数审核

位置：`server/xiangqi.mjs:448–454`。

22.2 规定审核提出方将军最多计 10 着。当前完全不读取 `check`，所有无吃子着数照计。**计数边界探针**：120 手记录、红方其中 12 手将军，函数仍返回 true；这只是计数单元探针，不声称构造了合法的完整 120 手对局。

需明确数字裁判如何触发及选择审核方，再按该方累计有效着数。现有 119/120 边界测试验证的是简化实现，不是完整规则。

### R7 / P2：双方无取胜可能的简单残局、协议和棋尚未完整接入

位置：`server/xiangqi-service.mjs:181–194`、`server/xiangqi.mjs:288–303`。

4.2.1、4.2.2 的协议和棋、双方均无取胜可能的简单局势未进入现有终局裁决。**已验证最小残局**：只剩不同列的两将，合法移动后仍是 `playing`；服务端后续也只有重复和自然限着两个分支。

简单残局只能收录有证明的类别，不能将任意看似缺乏攻击力的局面直接判和。认输已有服务端路径，不列为“完全未实现”。

### R8 / P2：重复签名按实例 ID，存在同类子互换漏检风险

位置：`server/xiangqi.mjs:458–459`。

**表示层探针已验证**：交换红方两枚车的实例 ID 与其坐标，按颜色、兵种、位置及轮走方看局面相同，但引擎签名不同。本次未构造合法的双车互换长序列，此项属于重复等价表示的风险，应补规则棋例验证。

局面等价签名和追捉时需要的棋子身份应分开保存，不能简单删掉所有历史棋子身份信息。

## 建议实施次序与验收

1. 先修 R1–R3，防止把允许着法错判负；按每手前后盘面记录攻击者、目标、威胁是否新产生及具体着法性质。
2. 用独立棋例裁决器实现将、杀、捉、兑、献、拦、跟、闲及相关例外，再处理双方责任。走法生成器和裁决器分层，避免大幅改动已验证的基本走法。
3. 补 R5 的待判/限期变着/终局状态，再补自然限着、简单残局与协议和棋。
4. 逐条导入规则书棋例与参考图，记录条款、初始局面、合法走子、双方着法性质、责任方、裁决时点及预期结果。尤其要有相同循环不同起点、红黑互换、双向攻击和重启续局测试。
5. R8 用棋例确认后完善局面等价。对外规则元数据区分“目标 CCA2020”和“已验证覆盖范围”；当前仅返回 `ruleset:CCA2020` 容易造成完整符合的误解。

**不能用“全部现有测试通过”替代棋例验收，也不建议用 LLM 自行判断这些胜负来补规则引擎。** LLM 应选着，确定性的服务端规则负责合法性和裁决。
