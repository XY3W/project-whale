# 刷新后聊天记录恢复修复

## 原因

原界面从 `/api/memory` 恢复对话，该接口固定只返回最近 24 条；同时，游戏/自主回合的部分角色台词仅发给页面而没有记录。前端还会在历史请求返回时检查聊天列表是否为空，只要已经出现一条新消息或思考行，就跳过整批历史。

## 实现

- 新增仅供界面使用的 `/api/conversation`，按当前签名 Cookie 所属用户隔离，以消息 ID 分页，每页默认 100 条；可通过“加载更早的对话”继续查看。LLM 的上下文选择和原近期 24 条窗口保持分离，不把全部历史塞进模型请求。
- 公开回复、执行计划台词和定时提醒统一在服务端记录并刷新落盘，再发给页面；覆盖普通聊天、游戏事件、自主回合、定时任务和无 Key 的测试回复。推理流不进入聊天存档。
- 消息有稳定 ID 与服务端序号。历史页、实时消息、用户本地回显及服务端确认按身份合并，不因文本相同就误删不同轮次。重复用户发送确认后不重新执行任务；已缓存回复重放使用原消息 ID。
- 首次历史 HTTP 请求完成后再建立主场景 WebSocket，明确签名用户 Cookie 的建立顺序。断线重连恢复缺失消息；漏过超过一页时持续补到已知消息，避免中间留洞。
- 历史加载失败显示重试入口，不默默略过；游标因清理或过期失效时重新同步。恢复期间的新消息和当前思考行保留。
- 新收到的完整文本不再被存储层截到 8000 字符。新客户端消息 ID 在普通 HTTP IP 页面也有回退生成方式，不依赖仅安全上下文可用的 `crypto.randomUUID()`。

仍沿用既有记录保留期限：`MESSAGE_RETENTION_DAYS`，默认 30 天。用户主动清理、已经过期或过去从未落盘的记录不能凭空恢复；仅被旧接口 24 条窗口隐藏、仍在存档中的消息可以重新查看。原已截断文本也不能补出被截掉的部分。

## 验证

实际发布源码全量测试 **340/340 通过**，`npm run build` 通过。

- `tests/conversation.test.mjs`：超过 24 条的分页、分页中新增消息、用户隔离、完整长文本、重复发送、同文不同消息、恢复与实时回显竞态、旧记录兼容。
- `tests/conversation-integration.test.mjs`：真实 HTTP / WebSocket 配隔离存档，验证 151 条旧消息可恢复、回复在客户端收到前已落盘、重复请求不重新执行、不同轮次同文回复不合并。
- `tests/xiangqi-wakeup.test.mjs`：本地模拟上游，JSON 和 tools 两种协议的自主象棋台词刷新可恢复，无真实模型费用。
- 浏览器使用纯验收数据：恢复 251 条历史过程中插入实时第 252 条，仍恢复成功且没有重复；模拟断线期间新增 150 条，补齐后顺序连续；加载更早消息后共 402 条，刷新后再次分页取回 402 条。截图见 [验收画面](review-evidence/chat-history-2026-11-01/preview.png)。临时验收页与服务已清理。

本次只修复聊天记录，不修改分层动画架构。
