- 人设主打“蠢萌”，整体安静。不要过度卖萌，不要话多，不照搬网上鲸鱼娘标签的全部性格。

## 3. 人设与提示词组织

### 3.1 安静蠢萌的具体表现

直接可用正文见 [llm-design/PERSONA_V2.md](llm-design/PERSONA_V2.md)。

- 反应有时慢半拍、带一点小迷糊，办事认真，有需要时自己简短纠正；不每轮表演“欸？数错了”。
- 默认一条简短回应，通常一句，必要时两句；不得为了凑两句附加可爱旁白。用户要求解释时允许正常解释，不以人设拒绝回答。
- 用户聊天回应其意思；自主扫雷、走路、拾取等普通过程默认 speech=""。只在有实际内容的结果、必要澄清或值得提醒的变化时开口。
- 不句句加“唔、欸、呀、呜、欸嘿”，不连续感叹号、颜文字，不每步说“好了”，不固定自称或每句叫用户。
- 微小表情和动作只能使用已启用的能力，不臆造“挠头、歪头”等尚未注册的工具；不为了蠢萌增加无关动作、故意失败或额外思考等待。
- 不自动加入“聪明爱摸鱼、傲娇嘴甜、女仆服从主人、爱吃白饭、拒绝被说胖”等整套标签性格。后续用户明确选择某项时再修订。

### 3.2 组装方式

建议将服务器现有大system拆成可维护的四部分，再按固定顺序组装为一个system：

1. 行为与事实契约：工具权限、事实来源、JSON输出、成功标准。
2. 安静蠢萌表达模块：只约束speech与已支持的表现，不降低决策准确性。
3. 当前已启用玩法的通用规则；具体场地数字和范围以动态注册表/快照为准。
4. 记忆使用规则：只用有来源的confirmed数据，支持纠正和遗忘。

本地文件是制作/交接源；服务器实际文件位置由DeepSeek整理，不在本地另开一套应用实现。能力说明、参数范围、Schema仍从同一注册表生成。避免把雷数、可走范围等动态配置长期写死在人设里。

每次请求附promptVersion、personaVersion、capabilityVersion和schemaVersion，用于追溯；不将原始用户消息、记忆或场景描述拼成新的system规则。人设更新从下一个新任务生效；进行中任务固定所用版本，行为协议变更另走原计划的版本校验。

### 3.3 网上标签的定位与取舍

`PERSONA_LOAD`这类格式可作为我们自己的角色卡表达，但不把它当成DeepSeek厂商保留命令、人格ID或功能开关。采用“可配置角色档案＋明确中文解释”的组织思路即可，本轮不依赖某个特定英文标签能否触发联想。

不自动安装Harness鲸鱼娘插件。它针对Harness会话注入人设，我们的角色通过服务器直接调用API，应用入口不同。也不照搬插件的全局共享记忆、强制称呼或自动人格成长。

标签逐项解释、公开源码与官方接口依据见 [llm-design/PERSONA_TAG_RESEARCH.md](llm-design/PERSONA_TAG_RESEARCH.md)。厂商是否在训练中使用过相关角色素材不能从输出表现证明，本方案不作这种断言。

## 4. 记忆闭环

### 4.1 消息先有身份与来源

用户消息先由服务端分配并持久化messageId、ownerScope、sessionId、role、content、createdAt，再交给模型。上下文提供允许引用的用户消息ID；模型提案不能靠“默认绑定当前消息ID”证明真实性。

提案至少包含key、value、sourceMessageId、sourceQuote及意图类型；每次最多两条。只接受既有四类：preferred_name、response_language、response_style、ordinary_interest。ordinary_interest可有多个独立条目，不能用一个新兴趣覆盖全部旧兴趣。

服务端核验：

- 原消息实际存在、属于同一owner，role为user，且在本轮可引用范围内。
- sourceQuote能在该消息原文中核对。用户转述、引号内的他人要求、假设或玩笑不能仅凭字符串匹配成为用户事实。
- 候选内容由原话支持，字段、长度、操作、版本合法；不能引用助手自己的台词、场景文字或历史摘要来制造新用户偏好。
- 自主回合没有有效用户来源时不收集个人记忆。记忆提案失败独立记录，不使合法动作重新执行。

### 4.2 确认、更新和删除

- 用户明确要求“记住”“以后叫我/以后回答……”且语义、来源无歧义：由服务端在核验后确认。含糊时保留candidate。
- 普通偏好陈述先进入candidate；聊天面板的记忆列表可非阻塞确认、修改或删除，不弹审批框打断动作。
- 模型不能自称已写入confirmed。回包必须区分候选已记录和偏好已生效。
- 用户明确纠正：同一称呼/语言/风格key的新声明覆盖旧值，旧记录标记superseded，并记录来源与revision。
- 用户要求忘记或删除：立即从检索、摘要、缓存和后续请求中排除。永久删除同时清理原值与派生副本；审计只留删除事件元数据，不保留被删原文。
- 删除后的旧摘要、重试回包和迟到提案不能把同一旧事实恢复；撤销来源与版本校验必须持续生效。用户未来明确重新提供并要求保存时，按新来源建立新记录。

最少记录：id、ownerScope、key、value、sourceMessageId、sourceQuote、status、revision、createdAt、updatedAt、supersedesId。有效状态区分candidate/confirmed/superseded/deleted。

### 4.3 回喂与存储

- 仅向当前owner的请求注入相关confirmed偏好；每次最多20条、目标预算800 tokens。无确认记忆时如实不知道，不借历史助手台词补造。
- 区分角色固定档案与用户偏好：角色是鲸鱼娘属于人设；用户喜欢什么属于个人记忆；角色位置、棋盘、持物和模式属于实时状态。
- 维持全场地一名执行者的规则，同时给个人数据绑定稳定、服务端签发的ownerScope。不能用每次服务重启新建的session时间戳当长期用户身份，也不能信任客户端随意指定别人的owner。
- 自主游戏默认不注入无关聊天和个人记忆；需要使用某个明确用户交代的未完目标时，作为有来源的任务携带。
- JSON存储增加schemaVersion、revision、串行写入/并发冲突处理；保持原子落盘。候选和confirmed分别计限额，候选积满不能使已确认偏好永远无法更新。SQLite迁移可另做，不阻塞此闭环。
- 原始对话按原方案默认保留30天，可配置；confirmed偏好保留到用户删除，来源摘录仅作为该偏好的证据保留。删除偏好同步清理其摘录；活动任务对账证据不被普通聊天清理误删。
- 用户界面明确区分“清空这段聊天”和“删除长期偏好”。不同owner不串读；开发日志不复制完整聊天或记忆值。

## 5. 会话、摘要与任务证据

### 5.1 三类上下文分别维护

1. 实时状态：当前位置/朝向、物品与槽位、公开棋盘、模式和预算，每次从程序刷新。
2. 任务工作记忆：原目标、已提交动作和不可重复事件、累计位移、失败/取消/unknown、最新版本与实际结果，从执行账本生成。
3. 会话背景：近期完整对话轮、早期会话摘要、相关confirmed偏好；不能成为新行动命令。

review同时收到本次执行报告和本任务累计进展。不能只因为早期成功步骤离开最近12条聊天就再执行一遍；也不能把一段“已完成”的文本摘要当成真实提交证据。

### 5.2 历史与摘要

- 不再把“最近12条消息”称为“12轮”。按完整对话轮裁剪，最多12轮，历史初始目标预算1200 tokens，受整请求预算约束；最新用户消息与当前目标单独必保留。
- 程序生成结构化任务/事件摘要，包含来源plan/step/event IDs。失败、unknown和已提交副作用不能被一句“上轮做完了”抹掉。
- 较早聊天维护不超过约600 tokens的会话摘要，标记derived、sourceMessageIds与更新时间；不把模型猜测升级成用户事实。
- 摘要可在已有planning/review响应中附可选summary_proposal，校验来源后更新；无额外闲置总结调用。提案缺失或不合法时，使用仍有效的旧摘要及相关原文，不阻塞动作、不虚构摘要。
- 新纠正和遗忘立即使相关旧摘要内容失效。摘要不保存当前坐标或推测的执行结果，不跨owner引用。
- 自主回合继续省略不相关聊天，明确historyOmitted；裁剪会话标记historyTruncated和droppedMessages，不能让模型误以为看到了完整历史。

### 5.3 完整请求预算

沿用当前工程输入阈值14000估算tokens；这不是DeepSeek模型本身的上下文上限。输出与思考预算继续由适配器配置，并校验输入＋输出预留不超所用模型上限，不在本方案偷偷改推理强度。

先实际组装messages，再对其全部内容估算，包括system、人设、phase模板、能力/Schema、上下文和输出协议。每段只计一次，不能一边在context里放capabilities、一边又在估算里重复加一份；也不能漏计模板和输出说明。tokenizer可用时采用实际计数，否则标注保守估算及余量。

裁剪顺序：无关历史/事件→无关偏好→最早完整对话轮；当前用户消息、原目标、世界关键事实、能力约束与必要任务证据不可删。关键内容仍超限时明确报错，不截断JSON、不削弱协议或偷偷丢掉失败状态。

## 6. 实施顺序与验收

| 阶段 | 交付与验收 |
| --- | --- |
| P0 人设 | 使用安静蠢萌模块；移除算数会数错/固定卖萌旁白；不增加模型调用；结构化动作准确率不因人设降低 |
| P1 来源与存储 | 有真实消息记录和owner；伪造引用、助手来源、跨owner来源均拒绝；原有动作不重试 |
| P2 记忆UI与回喂 | 明确记住可生效；普通陈述可确认；纠正/删除能更新后续模型输入；重启后仍正确 |
| P3 上下文 | 完整轮裁剪、会话摘要和累计任务证据；整messages预算可核对；自主回合不重放旧指令 |
| P4 综合验收 | 用真实聊天、扫雷、持物和恢复场景验证，记录调用次数、预算、来源IDs与结果，避免导出私人原文 |

关键用例：

- 连续普通动作和自主扫雷多轮保持安静，不每轮说“好了”或固定加语气词。
- 用户认真问问题得到清楚回答，不为蠢萌故意答错；求解与动作参数不含“人设随机错误”。
- 本轮user说“以后叫我小乔”：核验来源后确认，下次/重启可使用；不存在的sourceQuote不能确认。
- “我朋友说以后叫他小乔”不成为用户称呼；用户纠正或忘记后，旧摘要不能复活旧名。
- 关闭两分钟聊天保留上下文；清空聊天与删除偏好是不同操作。
- 历史超预算后仍保留原目标与已完成副作用；review不重复投掷、拾取、敲击或挖掘。
- 人设标签不改变能力范围、聊天计时、思考提示或物理；MODE_TAIL_FLUKES不能生成未注册骨骼指令。
- 变更personality不改变工具JSON字段、能力ID或坐标单位；LANG_ZH_CN_ONLY只约束公开speech。

用户确认的是本方案方向；具体代码仍由DeepSeek实施。完成状态须以后续代码与实际运行验收为准。
