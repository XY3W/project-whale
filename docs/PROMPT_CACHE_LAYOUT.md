# 提示词分段与缓存布局

2026-11-03。这份文档说明模型提示词的排列规则、为什么这么排，以及改动时怎么验证。
代码入口：`server/llm.mjs` 的 `composeUserContent()`、`moveHistoryBlock()`、`filterXiangqiHistory()`。

## 为什么要在意顺序

DeepSeek 的前缀缓存按 token **逐字**匹配：新旧两次请求从头开始相同的部分可以复用，
命中长度为"公共前缀"的长度。没命中的部分要重新算，既花钱又慢。
所以一条提示词要按"变化频率从低到高"排列，让最大的块尽量落在命中区里。

## 当前顺序（一次请求，从稳定到易变）

| 顺序 | 内容 | 变化频率 | 说明 |
| --- | --- | --- | --- |
| 1 | system：项目规则 + 人设 + 技能索引 | 很少 | 技能增删才变 |
| 2 | 阶段指令：planning/review 模板 + 条件段落 | 很少 | 只有对局开始/结束切换条件段落 |
| 3 | 输出契约 / 工具说明 | 不变 | 常量文本 |
| 4 | `XIANGQI_MOVE_HISTORY_JSON:` 棋谱块 | 每手**追加** | 旧内容是新一轮的前缀 |
| 5 | `REQUEST_CONTEXT_JSON:` 本轮快照 | 每手**改** | 位姿、盘面、回合、revision |
| 6 | 之后追加的 assistant / tool 消息 | 每轮追加 | 工具循环只往后接，不改前面 |

两条规则：

1. **只追加的大块放在原地会变的小块之前。** 棋谱每步加一条，旧的整段仍是前缀，所以能整段命中。
2. **每轮都改写的快照放最后。** 盘面 JSON 一改，它后面的一切都要重算；放最后就只重算它自己。

## 实测（走一手后，新旧提示词的公共前缀）

用 `tools` 模式的首个请求测量（system + user），棋盘每手更新一次：

| 走到第几手 | 提示词总长 | 公共前缀 | 命中率 |
| --- | --- | --- | --- |
| 11 | 10,913 | 10,585 | 97.0% |
| 51 | 16,273 | 15,945 | 98.0% |
| 101 | 22,975 | 22,646 | 98.6% |

反例（2026-11-03 实测）：只把棋谱挪到最末尾、快照留在它前面，100 手时公共前缀只有
9,148 字，命中率 **39.8%**——因为快照每手都变，它后面的棋谱就全部作废了。
棋谱体积约 134 字/手，100 手约 13.4 KB，是提示词里最大的一块。

## 工具循环里的刷新

`filterXiangqiHistory(messages, liveGameId, currentView)` 每次模型调用前执行：

- 把**所有**历史 tool 结果里的 `moveHistory` 剥掉，棋谱全上下文只保留末尾一份；
- 用 `currentView` 刷新末尾棋谱块和快照（工具循环中途走子提交后盘面会变）；
- 没有棋局（`currentView === null`，或没传且 `liveGameId` 为空）时，整块棋谱不发送。

## 改动时怎么验证

```bash
node --test tests/prompt-cache-order.test.mjs
```

该测试断言：棋谱在快照之前、棋谱不进快照 JSON、以及"走一手后公共前缀 ≥ 95%"。
新增每轮都会变的字段时，放进快照（第 5 段），不要加到指令或棋谱块里。

## 已知边界

- 工具结果每次调用都会 `JSON.parse` → 剥字段 → `JSON.stringify` 重新序列化；只要字段顺序稳定，
  字节就一致。若将来引入顺序不稳定的结构（如键顺序随机的 Map/对象），前缀会抖动。
- 快照里仍有放大余地：若能拆成"稳定段 + 易变段"，命中率还能再抬；目前快照只有约 0.5 KB，收益有限。
- 本轮只覆盖象棋链路；其他游戏没有这类大块，天然在命中区。
